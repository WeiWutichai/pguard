# pguard_profile_api (EXPERIMENTAL)
Guard + customer profiles and the guard onboarding-approval lifecycle (source of truth
for this service — codegen produces the Rust handler stubs/types, the Dart client, and
the TS client). Split out of the v1 `../guard-dispatch/services/auth` god-service.

Every endpoint here is **AuthUser-gated** (a registered, logged-in user — Bearer access
JWT, or the `access_token` cookie for web). There is NO phone-verify / profile-token
flow in this slice; that registration step is future identity work.

**PDPA — bank account masking (security-reviewer §7):** on the owner-facing read
(`GET /profile/me`) the `account_number` is returned MASKED to its last 4 characters.
The admin onboarding endpoints (`GET /admin/guard-profiles`) return the FULL value, as
the reviewer needs it to verify payout details.

**Role gates (403):** `POST/PUT /profile/guard` require role `guard`; `POST
/profile/customer` requires role `customer`; all `/admin/_*` endpoints require role
`admin`. A wrong-role caller receives a generic 403 that names the REQUIRED role, never
the caller's (no role enumeration).

Client-facing paths are served behind the gateway under the `/v1` prefix (CLAUDE.md
\"API versioning\"). Success responses use the standard `{ success, data }` envelope;
errors use `ErrorBody`.

**Documents:** a guard uploads their own credential IMAGES (id card, security license,
training cert, criminal check, driver license, passbook photo) via
`POST /profile/guard/{user_id}/documents` — multipart, magic-byte validated, stored in
private S3 under a server-generated key. Auth is logged-in guard, **own docs only** (so it
happens after approval, once the guard can authenticate); the owner or an admin reads a
document via the matching `GET` (short-lived presigned URL, never the raw key). Document
**expiry dates** are captured separately (metadata only) via `document_expiries` on the
guard profile submit — these feed the admin \"expiring documents\" surface.
