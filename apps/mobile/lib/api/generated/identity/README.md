# pguard_identity_api (EXPERIMENTAL)
The auth foundation (source of truth for this service — codegen produces the Rust
handler stubs/types, the Dart client, and the TS client). Identity ISSUES + manages
the user access JWTs that every other pguard service validates.

Ported from the v1 `../guard-dispatch/services/auth` god-service, split out and
hardened for v2:
  1. **Refresh-token rotation + reuse detection (RFC 6749 §6).** Each refresh is a
     single-use opaque token in a `family`; presenting an already-rotated token is
     treated as theft and revokes the whole family.
  2. **Force-revoke-all.** A per-user `token_revocation_version` (plus the Redis jti
     blocklist) lets incident response invalidate every outstanding access token at
     once. Exposed as a service-JWT'd internal endpoint AND driven by the
     `pguard.events.user.compromised` NATS event.
  3. **Generic 401 on login failure** — no user-enumeration; the password verify runs
     even for unknown identifiers (constant-time path).

Client-facing paths are served behind the gateway under the `/v1` prefix (CLAUDE.md
\"API versioning\"). Success responses use the standard `{ success, data }` envelope;
errors use `ErrorBody`. On login/refresh the token pair is ALSO set as httpOnly,
Secure, SameSite=Lax cookies (`access_token`, `refresh_token`) for the web admin.
