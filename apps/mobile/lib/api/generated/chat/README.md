# pguard_chat_api (EXPERIMENTAL)
v2 OpenAPI contract for the chat service (source of truth — codegen produces Rust handler
stubs/types, the Dart client, the TS client). 1:1 booking-scoped messaging between a
customer and the assigned guard, with image/video attachments and real-time delivery over
a WebSocket.

## v2 rules baked into the contract
  1. **N+1-free list.** `GET /conversations` resolves last-message, unread-count, and the
     counterpart's name/avatar in ONE query — entirely inside the `chat` schema. v1 JOINed
     `auth`/`booking` directly; v2 forbids cross-schema JOINs (CLAUDE.md → Data). The
     counterpart display fields are **booking-derived data the creator supplies inline** at
     `POST /conversations` and stored on `chat.participants` (API/event-derived, never a
     cross-schema JOIN).
  2. **Role-based alignment.** Bubble side + unread are decided by `sender_role` vs the
     caller's `acting_role` — NEVER by `sender_id`. The same user can be the guard in one
     conversation and the customer in another, so read receipts are tracked **per role**.
  3. **IDOR.** `list-messages` / attachment upload+signed-url / mark-read all require the
     caller to be a **participant** of the conversation (admin bypasses). The check is
     explicit; an authenticated non-participant gets `403`.
  4. **Read-only state.** When the linked booking is `completed`/`cancelled` the client
     disables send — and the **server also rejects** writes (message send + attachment
     upload) to a closed conversation. Never trust the client.
  5. **Events (outbox).** A sent message enqueues `pguard.events.chat.message_sent` in the
     SAME transaction as the message INSERT (transactional outbox); a background relay
     publishes it to NATS and notification consumes it. Chat NEVER writes notification's
     schema directly (no v1 fire-and-forget cross-schema INSERT).
  6. **Generic errors.** No enumeration / no internal leak.

## WebSocket — `GET /ws/chat`
Documented here because WS handshakes are not expressible as OpenAPI paths. See also
`contracts/asyncapi/chat-ws.yaml`.
- **Auth = `Authorization: Bearer <access-token>` on the upgrade request.** A token in the
  URL query is NEVER read → such a request is rejected `401` (no sensitive data in the WS
  URL). The session re-validates the token periodically and closes on expiry/revoke.
- **`conversation_id` is NOT in the URL.** After open, the client sends JSON frames
  `{ \"conversation_id\": \"<uuid>\", \"content\": \"...\", \"message_type\": \"text\",
     \"sender_role\": \"guard|customer\" }`. The server verifies the sender is a participant of
  that conversation and the conversation is writable, persists + emits the outbox event,
  and broadcasts `{ \"id\", \"conversation_id\", \"sender_id\", \"sender_role\", \"content\",
  \"message_type\", \"created_at\" }` to the other participant's live socket (Redis pub/sub on
  `chat:{conversation_id}` for cross-instance fan-out). Errors come back as
  `{ \"type\": \"error\", \"message\": \"<reason>\" }`.

Client-facing paths are served behind the gateway under `/v1`. Success responses use the
standard `{ success, data }` envelope; errors use `ErrorBody`.
