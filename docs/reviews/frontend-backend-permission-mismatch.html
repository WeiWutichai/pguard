#1 · Guard dashboard has no role check in initState()

frontend/mobile/lib/screens/guard/guard_dashboard_screen.dart:13-18
Issue
GuardDashboardScreen.initState() does not verify that AuthProvider.role == 'guard' before mounting the bottom-tab UI. The screen assumes its caller has done the check.
Documented intent
CLAUDE.md treats guard dashboard as guard-only. Should reject other roles.
Actual behavior
Trusts caller. Code-path: main.dart home selector branches on auth.role — so first-mount is safe. Deep-link / direct Navigator.push bypasses the check (e.g. notification tap, future deep-link, route restoration after suspended app).
Why it's LOW
Currently no production code path pushes GuardDashboardScreen directly — every entry funnels through main.dart. But the safety net is implicit; one future change can break it silently.
Recommended fix
Before @override void initState() { super.initState(); _ensureGpsServiceStarted(); }
After @override void initState() { super.initState(); WidgetsBinding.instance.addPostFrameCallback((_) { final auth = context.read<AuthProvider>(); if (auth.role != 'guard') { Navigator.of(context).pushAndRemoveUntil( MaterialPageRoute(builder: (_) => RoleSelectionScreen( phone: auth.phone ?? '', )), (route) => false, ); return; } _ensureGpsServiceStarted(); }); }
Tests to add
  • Widget test: pump GuardDashboardScreen with AuthProvider set to role='customer' → expect RoleSelectionScreen in tree after frame.
  • Widget test: pump with role='guard' → expect bottom tab bar rendered.
  • Widget test: pump with role=null (unauthenticated) → expect RoleSelectionScreen.
Low

#2 · GET /available-guards allows any authenticated user (should be customer-only)

services/booking/src/handlers.rs — available_guards() handler
Issue
Handler accepts AuthUser extractor but does not check role. Any authenticated user (admin/guard/customer) can call.
Documented intent
CLAUDE.md describes this as customer discovery — used by customer booking screen to find nearby available guards.
Risk
A guard could enumerate other available guards (competitive intel — knowing who else is online and their distance). Not a data exfiltration in classical sense (data is intended to be visible to customers), but the role boundary is wrong.
Why it's LOW
No PII leak (only public profile + distance). But it's the kind of inconsistency that compounds — if more discovery endpoints follow this pattern, attack surface grows.
Recommended fix
Before pub async fn available_guards( State(state): State<Arc<AppState>>, user: AuthUser, Query(params): Query<AvailableGuardsQuery>, ) -> Result<Json<Vec<AvailableGuardResponse>>> { // ... fetch guards }
After pub async fn available_guards( State(state): State<Arc<AppState>>, user: AuthUser, Query(params): Query<AvailableGuardsQuery>, ) -> Result<Json<Vec<AvailableGuardResponse>>> { if user.role != "customer" { return Err(AppError::Forbidden); } // ... fetch guards }
Tests to add
  • Integration test: GET /available-guards as guard JWT → 403
  • Integration test: GET /available-guards as admin JWT → 403 (or 200 if we decide admin should see; doc the decision)
  • Integration test: GET /available-guards as customer JWT → 200 + non-empty list
Decision needed
Should admin also be able to see /available-guards? Pro: admin's live map shows online guards; might want to test booking workflow. Con: admin has dedicated /admin/operations and /locations/all. Recommended: customer-only — admin uses dedicated endpoints.
Medium · highest priority

#3 · ChatListScreen accepts actingRole param without validation

frontend/mobile/lib/screens/chat_list_screen.dart + chat_screen.dart
Issue
Both screens accept a constructor param String? actingRole that is passed to ChatProvider.fetchConversations(role:) and ChatProvider.sendMessage(senderRole:). The screen does not verify that actingRole is one of 'guard' | 'customer' nor that it matches the authenticated user's role.
Documented intent
CLAUDE.md states "Chat scoped by acting role" — guard dashboard passes actingRole: 'guard', hirer dashboard passes actingRole: 'customer'. The role determines which counterpart name and unread counts are shown.
Risk (why MEDIUM)
A custom client (or a malicious build) could pass an arbitrary actingRole string. The backend trusts the query param ?role=guard on GET /conversations — it does NOT cross-check against the JWT's role claim. So a customer JWT with ?role=guard would return guard-side conversation list (still scoped by participant — they only see their own — but in the wrong "perspective"). Not catastrophic since participant check still applies, but the boundary is sloppy.
Two-layer fix (both required)
Frontend (mobile):
Before — chat_list_screen.dart class ChatListScreen extends StatefulWidget { final String? actingRole; // accepted as-is const ChatListScreen({this.actingRole}); }
After class ChatListScreen extends StatefulWidget { final String actingRole; const ChatListScreen({required this.actingRole}) : assert( actingRole == 'guard' || actingRole == 'customer', 'actingRole must be guard or customer', ); } // in initState: final auth = context.read<AuthProvider>(); final canActAs = auth.role == widget.actingRole || (widget.actingRole == 'customer' && auth.customerApprovalStatus == 'approved'); if (!canActAs) { Navigator.pop(context); return; }
Backend (chat service):
Before — list_conversations pub async fn list_conversations( user: AuthUser, Query(q): Query<ListQuery>, ) -> Result<Json<Vec<Conversation>>> { let acting_role = q.role .unwrap_or_else(|| user.role.clone()); // trusts query param }
After pub async fn list_conversations( user: AuthUser, Query(q): Query<ListQuery>, ) -> Result<Json<Vec<Conversation>>> { let acting_role = match ( q.role.as_deref(), user.role.as_str() ) { (None, r) => r.to_string(), (Some(r), "admin") => r.to_string(), // admin can act as either (Some(r), user_r) if r == user_r => r.to_string(), // user with single role can't impersonate the other _ => return Err(AppError::Forbidden), }; // ... }
Tests to add
  • Widget test: ChatListScreen(actingRole: 'admin') with assertion enabled → AssertionError (caught in debug).
  • Integration test: GET /conversations?role=guard with customer JWT → 403 (not 200).
  • Integration test: GET /conversations?role=customer with admin JWT → 200 (admin can act as either).
  • Integration test: GET /conversations?role=guard with guard JWT → 200.
  • Integration test: GET /conversations (no role param) with any JWT → defaults to user's own role, 200.

Recommended fix order

  1. Mismatch #3 first — it's MEDIUM and has a real backend gap. Fix both frontend assertion and backend cross-check together (single PR).
  2. Mismatch #2 second — single-line backend check + 3 integration tests. ~30 minutes.
  3. Mismatch #1 last — currently mitigated by app-root routing, but adding the check is defensive and trivial. Add when touching the file for any reason. ~15 minutes.

Also fix while you're there (audit found, not separate mismatches): add role check to LiveMapScreen.initState() (should reject guards/unauthenticated), and add explicit role check to POST /payments (currently relies on inference).
